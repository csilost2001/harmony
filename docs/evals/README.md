# AI の出力の評価セット

資料・スキル・tool の説明を変えたとき、**AI の出来が悪くならないか**を測る道具。LLM は使わない — 「この依頼で作って」と AI に頼んだ結果のワークスペースを、決めた期待で採点する。

## 使い方

1. 事例を見る: `npm run eval:design -- --list` (AI に渡す依頼が出る)
2. 空のワークスペース (または近いサンプルを複製したもの) に、その依頼を AI に頼む。変えたい資料・スキルの**前と後**で、それぞれ試すと比べられる
3. 採点する: `npm run eval:design -- <ワークスペース> [<事例の id>]` (終了コード 0 = すべて合格)

## 事例 (`docs/evals/cases/*.json`)

| id | 依頼の趣旨 |
|---|---|
| `crud-register` | 登録 API (入力チェック → INSERT → 201、重複は 409) |
| `search-list` | 検索 API (条件を確かめ → SELECT → 200、不正は 400) |
| `branch-status-update` | 状態を見て分岐する更新 (トランザクション、UPDATE、409) |

期待は**構造**で書く (名前に依存せず、種類・件数・参照・検査の結果で見る): `noIssues` (`designer__check_design` が 0 件) / `hasTable` / `hasFlow` (工程の種類・DB 操作・成功と異常終了の応答・使うテーブル) / `hasScreen` / `flowsCallable` (参照が切れていない) / `testViewpoints`。型は `backend/src/evals/runEval.ts`。

## 事例を足すとき

- `request` は、利用者がそのまま AI に貼れる文にする。依頼の最後に「`designer__check_design` で要確認を 0 件に」を入れる (入口の約束)
- `expectations` は、**正しい設計が複数ありえる**ことを許す緩さにする (名前は正規表現で幅を持たせる)
- 正解のワークスペースがあるなら `selfTest` にその場所を書く。採点の道具の試験が、そこで合格することを確かめる (採点の道具そのものの誤りを見つけるため)
- 事例の JSON が正しい形かは、試験が見張る

## 限界

- 採点できるのは**構造**だけ。業務の意味の正しさ (架空の値・SQL の別名の取り違えなど) は、`/review-flow` で目で確かめる
- AI の出力はゆれる。1 回の合否でなく、同じ依頼を数回試して、合格する割合で比べる
