# スキーマに関する提案 (設計者の判断待ち)

AI がこのシステムを理解しやすくするための改善提案 100 件 (2026-10-23) のうち、スキーマ (`schemas/v3/*.json`) に触れる 20 件 (53〜72) のまとめ。**スキーマは設計者の専権** ([ADR 0004](../decisions/0004-schema-designer-only.md)) なので、AI は変えていない。このうち**スキーマを変えなくても目的が達せた**ものは実施済み。残りは、設計者が決めるための材料をここにまとめた。

進み具合の全体: [ai-improvement-100.md](ai-improvement-100.md)

## 2. 設計者の判断が要るもの

効果が大きい順。**推奨**は AI の意見で、決めるのは設計者。

### 57. 参照の種類を、スキーマで宣言する (`x-ref-kind`) — **推奨: 最初にやる**

- **困っていること**: 「この項目は、どの種類の設計を指す id か」(`tableId` はテーブル、`targetScreenId` は画面 …) が、コードのあちこちに別々に書かれている。参照元の検索 (`references.ts`)・改名 (`renameEntity.ts`)・付け替え (`designReplace.ts`)・影響分析・今回足した参照の整合の検査 (`analysis/integrity.ts`) は、それぞれ**参照の場所を自前で持つ**。スキーマに参照の場所が増えると、どれかが取り残される (今回の回帰試験で、検査の穴が 8 つ見つかったのも同じ原因)。
- **提案**: id を持つ項目に、注釈を足す。例: `"tableId": { "$ref": "common.v3.schema.json#/$defs/EntityId", "x-ref-kind": "table" }`。AJV の strict は `false` なので、未知のキーワードは無害。
- **効果**: 参照の検査・改名・付け替え・補完・MCP の案内が、同じ宣言から作れる。新しい参照を足すときの取りこぼしがなくなる。
- **影響**: 既存の動作は変わらない (注釈だけ)。注釈を足す箇所は、処理フロー・画面・テーブル・業務フロー・帳票で数十か所 (実数は実装前に数える)。消費側 (上の 5 つ) を、注釈を読む形に順に移す — 移行の途中でも、今のコードのまま動く。
- **リスク**: 注釈とコードの二重管理の期間ができる。試験 (注釈の一覧 = コードの参照の一覧) で見張れる。

### 60. 状態遷移・初期データ (ISSUE #1499)

- 第 3 弾のスキーマ追加として、すでに設計者の判断待ち (状態遷移・初期データなど)。この提案群では扱わない。設計書の「終わり方の一覧・状態遷移図」(94) はこれが先。

### 56. 変数・入出力の型を、スキーマで持つ

- **困っていること**: 式の中の変数の型 (数 / 文字列 / 一覧) が、スキーマにないので、型の食い違い (文字列と数の比較など) を検査できない。「結果は 1 件か一覧か」は SQL から推定している (断定できない)。
- **提案**: `outputBinding` に型 (`type` / `shape: one | list`) を任意で持たせる。入力 (`inputs[]`) は型を持っている。
- **効果**: 式の型検査、SQL の結果の形の断定、生成コードの型。
- **影響・リスク**: 大きい。式言語 (js-subset) の型の規則が要る。**57 のあとに、まず `outputBinding.shape` だけ**を任意で足し、効果を見てから広げるのを推奨。

### 66. ドメイン型に、単位・丸め規則

- **困っていること**: `DomainEntry` (`type` `constraints` `uiHint` `description`) は、金額の通貨単位・小数の丸め (四捨五入 / 切り捨て) を持たない。生成コードで丸めがずれる原因になる。
- **提案**: `unit` (例: JPY) と `rounding` (`half-up` など) を任意で足す。
- **影響**: 小さい (任意の項目の追加)。create-flow の金額の扱いの規則と一緒に。

### 63. 処理フローの呼び出しの契約

- スキーマの変更は**不要**かもしれない: アクションは `inputs[]` / `outputs[]` を持つので、共通処理の呼び出し (`commonProcess` の `argumentMapping`) を、呼び出し先の入力と突き合わせる検査は、今の形で足せる。要望があれば実装する (スキーマは変えない)。

### 61. 工程ごとのテスト期待 (given / when / then)

- 処理フローにはテストシナリオ (`testScenarios`) がすでにあり、観点表も導出される。工程単位の期待を足す必要性は薄い。**推奨: 見送り**。

### 58. `x-ui` / `x-ai` (ラベル・入力ヒント・AI への注意書き) をスキーマに

- ラベルは今、コード側にある。スキーマに移すと、画面・資料・AI の案内を 1 か所から作れるが、日本語のラベルでスキーマが大きくなる (92KB がさらに増える)。57 の注釈で足りる部分が多い。**推奨: 見送り** (57 のあとに再検討)。

### 71. `x-deprecated` と別名

- 廃止する項目が出たときに必要。いまは廃止の予定がない。**推奨: 最初の廃止が出たときに**。

## 3. 見送ったもの

| # | 提案 | 理由 |
|---|---|---|
| 59 | 画面項目と DB カラムの結びつきの宣言を 1 か所に | すでに `binding` (`kind: tableColumn` + `ref`) がある。検査 (`integrity.ts`) と列対応表 (`analyze_design column-map`) が、これを使う |
| 68 | 大きな処理フローを複数ファイルに分ける (`include`) | 保存・編集・差分・検査の全層に及ぶ。処理を分けたいなら、共通処理 (`commonProcess`) に切り出せる。「流れ」表示は 1000 工程でも 2 秒で開く (計測: [process-flow-story-view.md](../spec/process-flow-story-view.md)) |
| 72 | スキーマの版の移行の登録 | 移行の枠組み ([schema-migration.md](../spec/schema-migration.md)) はあるが、移す対象がない。リリース前で、後方互換の必要もない |

## 4. 決めるとき

1. まず 57 (注釈だけ。動作は変わらない) を決める。採用なら、AI が実装・試験まで進められる

3. 56 は 57 のあと、`outputBinding.shape` だけから
