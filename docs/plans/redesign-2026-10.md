## 設計者判断 (2026-10-08 確定)

| 論点 | 判断 |

### 設計者判断 (2026-10-08 追加)

報告書 (HMY-REPORT-001) の判断事項 4 点について、設計者から「すべて了解。作業ブランチでの開発なので理想どおりに進めてよい」との回答。方針は次のとおり。

- 旧エディタ (GrapesJS / Puck) は削除する。ただし**先に「プロジェクト独自部品」を業務部品デザイナ上で WYSIWYG に作れるようにする** (JSON の手書きは現実的でないため)。削除はその後
- 独自部品 = 部品の木の断片に名前と「差し込み口 (パラメータ)」を付けて登録したもの。使う側は参照ノードで置く。デザイナで部品を組み、範囲選択 →「部品として登録」→ 差し込み口を指定、の操作で作る
- 独自部品の定義と参照ノードは screen スキーマとは別の追加になる。設計者の包括的な了承 (上記) を受けて作業ブランチ上で進めるが、スキーマ追加の内容は仕様書 (`docs/spec/`) に先に書き、報告書で確認を取る
- 段階 4 (権限 → 業務フロー → 帳票) も同様に進める。push / PR は別途指示があるまで行わない

### 残課題 (設計者判断が必要)

- 旧エディタ (GrapesJS / Puck) の完全廃止: 業務部品デザイナに無い機能 (Puck の外部 React 部品、カスタムブロック、キャンバス上の描画マーカー、ページレイアウトの合成プレビュー) の扱いを決めてから削除する。現状は「旧デザインの中身がある画面」と「Puck を明示選択した画面」だけが旧エディタで開く
- 段階 4 の各設計書はスキーマ追加 (設計者承認) が前提
- uuid を持たない設計ファイルは初回読込時に backend が uuid を書き足す (明示保存モデルの例外)。サンプルは全件 uuid 付きのため現状は発生しない

### 作業中に修正した既存不具合

- 同時読込で設計書が「見つかりません」になる: 保存が「切り詰めてから書く」方式で、並行して読んだ側が空 / 途中の JSON を読んでいた。一時ファイル + rename に変更し、読込時の uuid 補完もファイル単位で 1 本化 (`backend/src/projectStorage.ts`)。table-edit E2E の間欠失敗 (main でも発生) の根因
- 旧デザイナを開く / 閉じるだけで画面項目が汚染・削除される (`frontend/src/grapes/screenItemsSync.ts`)
