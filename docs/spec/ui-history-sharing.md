# 履歴・比較・共有・書き出し — 仕様書 (UI 改善提案 続編 第 9 弾)

**Status**: 実装済 (2026-10、ISSUE #1522)
**関連**: [file-backup.md](file-backup.md) (保存前の版) / [integration-ops.md](integration-ops.md) (レビューと承認・変更の記録・体裁と改訂履歴) / [ui-editing-depth.md](ui-editing-depth.md) / [ux-operations.md](ux-operations.md)

設計の変わり方をたどり、比べ、人へ渡す。**原本 (設計の JSON) は書き換えない** (書くのは、これまでの保存・設計書の体裁の設定だけ)。スキーマは変えない。覚えるもの (メモ・試作・通知の受け取り方) は、このブラウザにだけ置く。

## 1. 設計のあゆみ (ヘッダーの時計の印 / コマンドパレット「この設計のあゆみ」)

いま開いている設計 1 件 (画面・テーブル・処理フロー・業務フロー・帳票・シーケンス・DB ビュー・ビュー定義・ページレイアウト) の、6 つのタブ。中身が大きいので、開いたときに読み込む。実装: `components/history/` / 純関数は `utils/designHistory.ts` ほか。

| タブ | 内容 | 実装 |
|---|---|---|
| 変更の記録 (#162・#171) | この設計を、誰が・いつ・何をしたか (保存・削除・改名)。最終編集者を先頭に出す。**変更の記録 (監査ログ)** から引く。記録の対象は、画面からの保存は設計の id、編集セッションの保存は「種類 id」なので、動作の文言と合わせて種類を取り違えない。**AI (MCP) の変更**も載る: 動作が「AI が <tool> を実行した」の記録のうち、設計を変える tool を、tool 名と対象の id から引く (対応表は `shared/src/ops/auditTools.ts` の `aiToolDesignKind`)。対象の id は、引数から (ページレイアウトも)。`add_*` は結果の文の「ID: …」から作られた設計の id、`rename_entity` は新しい id。編集セッションの tool (`editSession__save`) は、実行の前に編集セッションから「種類 id」を引いて記録し、版の書き戻し・改名・スキーマ移行は、記録の備考の種類 (resourceType / entityType) から引く。**数えないもの**: 編集セッションの下書きの更新 (`editSession__update`。保存で、はじめて原本が変わる)・マーカー・レビューコメント・拡張の定義・複数の設計にまたがる付け替え・`save_all` など (理由は `AI_TOOLS_NOT_ATTRIBUTED`)。backend の試験 (`ops/auditTools.test.ts`) が、書き込みの tool を全部数え上げて、「対応表にある」か「数えない理由がある」かを確かめる (新しい tool を足すと、どちらかに入れるまで落ちる)。予行 (`apply` を付けない呼び出し) は、監査ログに残さない | `utils/designHistory.ts` |
| 版を比べる (#163・#164) | 保存前の版・いまの保存済みの内容・試作から、任意の 2 つを選んで比べる。**人の言葉の要約** (「カラム『金額』の長さの変更 (10 → 12)」) を先頭に、場所ごとの前 → 後の表。差の取り方は、編集中の「変更点」と同じ (id のある配列は id で対応づける。updatedAt は無視)。**コミットメッセージ (1 行目 72 文字 + 箇条書き)** と **レビュー依頼の文 (概要・変更点・確認してほしい点)** としてコピーできる | `utils/versionCompare.ts` |
| 完了の確認 (#172) | 要確認・命名規約・マーカー・レビューコメント・承認・成熟度を、**自動で判定**。判定できない項目 (種類により、指摘を設計ごとに分けられない・承認が無い) は「判定できない」とし、完了の判定に使わない。設計の中身の正しさは判定しない | `utils/completionChecklist.ts` |
| メモ (#173) | 自分だけのメモ。**原本にもマーカーにも書かない** (このブラウザの localStorage、ワークスペースごと)。「今日やることに出す」の印で、ダッシュボードの「今日やること」(下書きの次) に出る | `utils/personalNotes.ts` |
| 共有・書き出し (#169・#179) | **この設計だけの設計書**: HTML / Word / Markdown (画面・テーブル・処理フロー・業務フロー・帳票)。**原本ファイルの場所**のコピー (相対・絶対・AI への依頼文の出だし)。RPC `fileVersions.locate` | `utils/singleDesign.ts` / `shared/src/export/markdown.ts` |
| 試作 (#178) | 設計の内容を名前をつけて「試作」として残し (編集中の下書きがあればその内容、なければ保存済みの内容。1 つの設計に 5 件・1 件 400 KB まで)、本体と比べる・編集中の画面へ読み込む (保存するまで原本は変わらない) | `utils/trialSnapshots.ts` |

ヘッダーの時計の印の吹き出しに、最終編集者を出す。一覧 (テーブル・画面・帳票・業務フロー) の更新日の下に、最終編集者を小さく出し、自分が最後に編集したものには「(自分)」を付ける (`hooks/useLastEditors.ts`: 1 回の問い合わせで引き、30 秒は使い回す)。

## 2. 保存前の版の復元 (#161)

**ページレイアウト**にも広げた (backend `fileVersions` の対象に `page-layout` を追加。画面の履歴の「保存前の版」・MCP `designer__list_versions` / `restore_version`)。画面 (screen-item)・ガジェット (画面の一種) は、編集内容が複数のファイルに分かれるため対象外のまま。汎用定義は、編集画面に履歴の画面が無いため、対象にしていない。

## 3. レビュー (#165・#166)

- **宛先 (@名前)**: 本文に `@名前` を書くと、強調して描く (自分宛ては目立たせる)。名前は、これまでにコメントを書いた人・承認の操作をした人から、ボタンで足せる。「自分宛て」で絞れる。**通知は送らない** (利用者名は自己申告で、宛先は「その人に読んでほしい」という印)。返信・解決は、もとからある
- **解決済みの畳み**: 解決済みのスレッドは、やりとりを畳んで残す (「N 件のやりとり (解決済み)」を開くと、返信もできる)
- **進み具合 (レビューと承認)**: 状態ごとの件数 (未申請・下書き・承認待ち・差し戻し・承認済み・承認後に変更)・未解決のコメントのある設計の数。**止まっているレビュー**: 承認待ち・差し戻しのまま、1 / 3 / 7 / 14 日以上動かないものを、古い順に出す (既定 3 日)。`utils/reviewProgress.ts`

## 4. 書き出し・共有 (#167・#168・#170・#175)

| 項目 | 内容 |
|---|---|
| PDF (#167) | **ブラウザの印刷で「PDF に保存」**。設計書は /document の「別タブで開く」から印刷すると、表紙・目次・改訂履歴つきの紙面になる。**PDF を直接作る機能は持たない** (日本語の文字を埋め込む部品が無く、画像だけの PDF は文字を選べないため) |
| 印刷用スタイル (#168) | 編集画面からそのまま印刷したとき、ヘッダー・タブ・パンくず・編集のバー・通知を隠し、画面の高さの固定を外して全体を流し込む。表の見出しはページごとに繰り返し、行・工程カードの途中では改ページしない。`styles/print.css` |
| 読み取り専用スナップショット (#170) | 設計書の単体 HTML (CSS 同梱・目次・図つき) に、**文書内の検索** (章・節の本文に含まれるものだけを残す) と、「読み取り専用の写し (生成日時)」の注記を足した。1 ファイルで、メール・共有フォルダで渡せる。検索の script は 1 つだけで、設計の文字は textContent としてしか読まない |
| 書き出しの設定 (#175) | 形式 (HTML / Word / Excel) と載せない章に名前をつけて保存し、ワンクリックで出し直す。**保存先は設計書の体裁** (`document-template.json` の `exportPresets`。20 件まで) で、プロジェクトの全員が使える。設計書の画面の「書き出しの設定…」 |

## 5. 運用 (#174・#176・#177・#180)

| 項目 | 内容 |
|---|---|
| 取り込みの予行 (#174) | DDL の取り込みの予行 (新規 / 既にある・選んだものだけ取り込む) は、もとからあった。今回は、**既にあるテーブルとの違い**を、変更なし / 違いの一覧 (カラムの追加・削除・型や桁の変更) で見せる。**上書きは、しない** (列の id が変わると、外部キー・画面項目の参照が切れるため) |
| 通知の受け取り方 (#176) | ヘッダーの通知の履歴の「通知の受け取り方」。種類 (保存・成功 / お知らせ / 失敗) ごとに「必ず出す / まとめて出す / 出さない」と、**静かな時間帯** (日をまたぐ範囲も可。保存・お知らせを出さない。失敗は出る)。どの選び方でも、通知の履歴には残る。**まとめて**は、4 秒貯めて 1 つにする。`utils/notifyPrefs.ts` |
| 期間のまとめ (#177) | 変更の記録の画面の「期間のまとめ」。期間 (既定は直近 7 日) の、変更した設計・承認の動き・解決したマーカーとコメント・いま残っている要確認を、文章と表にして、コピーできる。設計を新しく作ったのか既存を変えたのかは、記録から分からないので分けない。`utils/periodSummary.ts` |
| 改訂履歴の下書き (#180) | 「更新から下書き」は、もとからあった (保存前の版から、前回の改訂のあとに更新された設計を拾う)。今回は、**期間の始まりを選べる**ようにし、変更の記録から**誰が変えたか**を添える |

## 6. できないこと・範囲を絞った点

- 画面・ガジェット・汎用定義の、保存前の版の復元と比較 (§2)
- 「この時点と比べる」を、変更の記録の 1 行ごとには付けていない。版を比べるタブで、保存前の版を選ぶ (保存前の版は 1 ファイル 20 世代まで)
- 試作から元への反映は、**内容全体の入れ替え** (項目ごとに選ぶ機能は無い)。編集中の画面へ読み込み、「変更点」で確かめ、Ctrl+Z で戻せる
- 宛先への通知、レビューの期限、フォルダを開く操作 (ブラウザからはできない)、PDF の直接生成
