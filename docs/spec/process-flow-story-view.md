# 処理フローの「流れ」表示 (読むための画面)

> 対象: 処理フロー編集画面 (`/process-flow/edit/:processFlowId`) の表示形式「**流れ**」
> 実装: `frontend/src/components/process-flow/story/`
> 経緯: ISSUE #1530 (設計者承認 2026-10-19)

## 目的

AI が詳細化した複雑な処理を、**人が全体から詳細まで把握する**ための、読む画面。いまの「カード」は 1 工程ずつ書くのに向くが、分岐・繰り返し・まとまりの中身も条件も、開くまで見えない。複雑な例 (47 工程・出口 12・変数 13 の受注登録) で評価し、次の 3 点が足りないと分かった。

1. 入れ子と条件を、一目で読む
2. 「どう終わるか」と「変数がどこで作られ、使われるか」を調べる
3. 人が確かめ終えたことを残す

> **設計書・「表」表示にも、同じ言葉を出す**: 条件を言葉に直す処理 (`expressionText` / `buildVarLabels` / `conditionText`) は、`@harmony/shared` の `flowWords.ts` に置き、設計書 (HTML・Word・Excel・Markdown の元の HTML) の処理記述表・テスト観点の到達条件と、編集画面の「表」表示の「条件・備考」でも使う (工程の実行条件 `runIf` も同じ)。**判定表の計算も `flowDecision.ts` に置き、設計書の処理設計に、複合条件の分岐の判定表 (読むだけ) として出す** (テスト観点は、`conditions` はもとの文字のまま、言葉は別の欄 `conditionWords` に持つ。テスト生成などの入力は変わらない)。言葉の下に、もとの式を小さく添える (式でない条件 (tryCatch など) は言葉だけ)。言葉にできない式は、もとの式のまま。顧客に渡す設計書でも、`@customer == null` が「取引先 が ない」と読める。

## 表示のしかた

表示形式の切り替え (カード / **流れ** / アウトライン / 図 / 表) に「流れ」を足した。同じ編集画面なので、編集セッション・工程の選択・タブ・取り消し (Ctrl+Z)・保存は、ほかの表示形式と共有する。**閲覧中は読むだけ**。編集中は、「その場で直す」窓口が出る (下の「その場で直す」)。細かい欄 (SQL・入力チェックのルールなど) は、行の「カードで開く」、またはダブルクリックで、カードへ移って直す。

| 見どころ | 内容 |
|---|---|
| 入れ子 | 判定は「もし〜なら」の枠。繰り返しは囲み。トランザクションは「ここから 1 まとまり … ここまで」の帯。承認の結果・入力チェックの不正の道・確定 / 取り消しのあとの処理も、枠で出る |
| ガード | 腕が 1 つで、その中が「返す」だけの判定は、「〜なら → 422 …」の 1 行にする (「ガード」の印)。それ以外の道は、次へ進む |
| 条件は言葉で | `@customer == null` → 「取引先 が ない」。式そのものは「実装」で出す。**意味を変えない**ことを最優先にする: 「かつ」の中の「または」は括弧で残す (`A かつ （B または C）`)。三項演算子・`??`・関数呼び出し・変数だけの式 (`@x`。真偽値とは限らない) は、そのまま式で出す。tryCatch・更新 0 件・外部呼び出しの結果も言葉にする |
| 実行条件 | `runIf` は、どの行 (ガード・繰り返しの枠・「次の行へ」を含む) にも、「↳ 〜のときだけ」と出す |
| 拡大縮小 | 概要 (見出しと 1 行。入れ子は畳む。実行条件 (runIf) だけは残す) / 詳細 / 実装 (SQL・式・変数の名前まで)。選びは、ブラウザに覚える |
| 見出し | `heading` のある工程から、新しい区切りを始める。帯をクリックで畳める。見出しが 1 つも無い流れは、区切らない |
| 番号 | 最上位は 1, 2, 3…。入れ子は、`3-A-1` (3 番の判定の、腕 A の 1 番目)・`6-確-1` (まとまりの、確定したあと)・`4-承-1` (承認されたら)・`1-NG-1` (入力が不正なら)・`7.1` (繰り返し・まとまりの本体)。同じ番号が 2 か所に出ないようにする |
| 出口 | この処理が終わるすべての「返す」(入力チェックの「不正のとき返す応答」を含む) と、そこへ行く条件の道すじ (状態コード順)。クリックで、その行へ (「概要」のときは、詳細に切り替えて) |
| 変数 | 作る場所 (結果変数・繰り返しの 1 行・入力エラー・捕まえたエラー) と、使う場所。選ぶと、流れの上で光り、前 / 次へ移れる。参照の形は `@x`・`@var.x`・`@var.action|loop|flowParameter|global.x`・`@var.step|tx.<工程>.x` を、その名前の変数として数える。この処理の中で作られない値 (入力・規約・セッション) は、変数のボタンにせず、書かれた名前のまま出す |
| 確認済み ✓ | 行ごとに付ける。進み具合を出す。確かめたあとに、その工程の内容が変わると、印は外れて「変更あり」と出る (ガードは、中の「返す」も指紋に含める) |
| 入れ子の見出し語 | 「このあとに続けて」は `subSteps` (親の本体のあとに、順に実行される。繰り返しなら全周回のあと、分岐なら選ばれた腕のあと) |

## その場で直す (編集中だけ。第 2・3 弾)

| できること | しかた |
|---|---|
| 工程を足す | 行の間の「＋」(行の間にカーソルを置くと出る。空の枠には「＋ 工程を足す」)。検索つきの「ここに何をする？」が開く。**ひな型**を選ぶと、必要な欄が空の状態で入り、続けて直す欄 (条件・テーブル・応答・説明) が開く |
| ひな型 | ガード (〜なら返す)・1 件取得して無ければ返す (取得 + ガード)・DB・入力を確かめる・明細を 1 行ずつ繰り返す・1 まとまり (失敗したら全部取り消す)・承認を取る (却下・期限切れの道つき)・外部に問い合わせる・計算して覚える・結果を返す・イベント・ログ。すべての種類は「ほかの種類」から |
| 日本語で頼む | 「ここに何をする？」の下の欄。AI に、位置つきで頼む (既存の AI の変更案の確認画面で、内容を確かめてから反映) |
| 説明を直す | 行の説明をクリックして書き換える (Enter で確定、Esc でやめる) |
| 条件を直す | ガード・「もし〜なら」・実行条件 (「＋ 実行条件」) をクリック。**どの値を / どうなら / 何と比べる**の選びで作る (式は自動で作られ、言葉と式が同時に見える)。値の候補は、その工程より前で作られる変数・入力・処理の外の値 (ambient)・DB の検索結果の列 (SQL の別名) など。条件を足せる (かつ / または。どちらか 1 種類)。括弧・関数などは、「式を直接書く」。足りない部品は決められず、まだ作られていない変数は、知らせる |
| テーブル・操作・応答 | 印 (テーブル・検索 / 登録…・返す応答・「不正なら → 400」) をクリックして選ぶ |
| 結果の変数 | 「→ 取引先」の印、または「＋ 結果の変数」(編集中は、印をクリックすると、直す窓が開く。作る場所・使う場所を光らせるのは、「変数」の一覧から)。呼び名 (日本語) と名前 (英字。形式と重なりを確かめる) を直す。**名前を変えると、使っている式の `@旧名` も直る** (まとまりが公開する内側の変数は、`expose` と `@var.action.<TX の名前>.旧名` も) |
| 動かす | 行の ↑ ↓、行にフォーカスして Alt+↑↓、または持ち手 (⠿) のドラッグ (行の間へ。別の枠へも動く。自分の中へは動かせない) |
| 消す | 行の ×、または行にフォーカスして Delete。取り消しは Ctrl+Z。消したときの通知に「元に戻す」ボタンが出る (9 秒間。**消した直後の状態のときだけ効く**: そのあとに Ctrl+Z・ほかの表示での編集・AI の反映などで下書きが変わっていたら、効かない。別の操作を戻してしまわないため。そのときは、Ctrl+Z で順に戻す) |
| 別の枠へ移す | 行の「移す」で、行き先 (最上位・道・「それ以外」・繰り返し / まとまりの中・承認の結果・確定のあとなど) を一覧から選ぶ (その枠の最後に入る)。ドラッグの代わりに、キーボードだけで使える。自分の中・自分の子孫の中は、行き先に出ない |
| 入力チェックのルール | 「ルールの印」または「＋ ルールを足す・直す」。対象の入力・種類 (必須・最大 / 最小の長さ・範囲・形式・選択肢)・値・違反したときの動き・メッセージを、一覧で足す・直す・消す。`@conv.limit.x` などの参照は、そのまま書ける (値の欄に `@` から)。「独自の式」の種類と、触らない項目は、そのまま残る |
| SQL | 「条件: …」の印、または「SQL を直す / ＋ SQL を書く」。文字の欄に、テーブルの物理名・入力の値を、選んで入れられる。SELECT の列は、条件の変数の候補に出る |
| 承認者と期限 | 承認者の印、または「＋ 承認者・期限」。役割・呼び名の一覧と、期限の式。承認の種類 (順番・同時・定足数) とエスカレーションは、カードで直す |
| 外部システムの呼び方 | 接続先の印・HTTP の印。接続先 (登録された外部システムから選ぶか、camelCase で書く)・メソッド・パス・待つ秒数・「返事は待たない」 (HTTP の呼び方のチェックを外すと、パス・リクエストの中身も消える)。リクエストの中身・認証・サーキットブレーカは、カードで直す |
| 結果の作り方 | 結果の変数の窓の「作り方」: 上書き / 足し込む (合計) / 一覧に 1 件ずつ足す。足し込む・足すときは、最初の値 (0・[]) も持つ (繰り返しの中で、合計や一覧を作るとき) |
| 見出し | 行の「見出し」で、その工程から新しい区切りを始める。見出しの文字をクリックで書き換え、「見出しを外す」で外す。**見出しは位置に付く** (工程を動かしても、区切りの位置は変わらない。見出しのある工程を消す・最上位から出すときは、次の工程が引き継ぐ) |
| 道・枠 | 判定に「＋ 道 (条件) を足す」「＋ それ以外」、道の ×。承認の「承認されたら / 却下されたら / 期限が切れたら」、まとまりの「確定したあと / 取り消したあと」、入力チェックの「不正なときの処理」を「＋」で足す |
| 検査の指摘 | 検査 (警告・エラー) のある行に、「⚠ N 件」の印 (重なると、内容が出る) |

どの操作も、編集中の下書きを直すだけで、保存は、いつもの「保存」。1 回の操作が 1 回の取り消しの単位。工程の ID (`step-NN` / `br-NN`) は、流れ全体で重ならないように採番する。

## 検索の結果は 1 件か一覧か

検索 (SELECT) の結果を入れた変数は、**1 件を探す形**と**一覧になりうる形**で、使い方が変わる (一覧は、0 件でも「ない」にならず、項目は `x[0].列` で読む)。この区別は、schema・仕様書のどこにも決まりがない (サンプルの書き方は混在している)。そこで、SQL から**推定**して知らせる (断定はしない)。

- 1 件とみなす: `LIMIT 1` / `TOP 1` / `FETCH FIRST 1`・集計だけ (`COUNT` `SUM` など。`GROUP BY` なし・窓関数なし)・**1 行を決める列 (主キー・一意の列・一意制約・一意インデックス) がそろった一致** (`WHERE` の `AND` でつないだ「列 = 引数」。`OR` や `IN` は数えない)。結合 (JOIN) は、結合先の主キーなどで結ぶ「多対 1」だけが許される (子の行を結ぶと一覧)。テーブルの定義が分からないときは、列 `id` の一致を主キーとみなす。それ以外は一覧とみなす
- 見るのは、いちばん外側の文だけ (コメント・文字列・括弧の中の部分クエリ・窓関数の中は見ない)
- 一覧とみなした検索の行に、「結果は一覧」の印 (ホバーで説明)
- 条件の選びで、一覧とみなした検索の結果を、①「ない / ある」で調べている ②項目を直接 (`x.列`) 指している、ときに案内を出す。「件数が 0」「件数が 0 より大きい」「1 件目の値 (`x[0].列`)」にワンクリックで直せる。**案内は「1 件を返す設計なら、このままで正しいので、直さないでください」と添える** (実行側が 1 件 (なければ null) を返す設計だと、`x.length == 0` は常に偽になり、「見つからない」のガードが効かなくなるため)。項目の候補に「件数」(`length`) も出る
- 実サンプル 58 件の検索 (examples/* の `outputBinding` つき SELECT) で、テーブル定義を使って判定し、「一覧と推定されたのに、1 件として使われている」ものは 0 件 (`.some(…)` など一覧のメソッドを除く)。推定は目安で、`LIMIT 1` を付けると、確実に 1 件になる

## 判定表 (複合条件を表で見る・直す)

判定 (分岐) の行の「▸ 判定表で見る」(複合条件の「ガード」にも出る) で開く。**条件の行 × 道の列**の表にして、組み合わせを一目で読み、直す。

- 見方: **○** その条件が成り立つ / **×** 成り立たない (反対の条件。`==` の反対は `!=`、`>` の反対は `<=`、「ない」の反対は「ある」) / **－** 関係しない。最後の行「そのとき」は、その道で行うこと (最初の工程。返すなら状態コード)
- 道は、**上から順に調べて、最初に成り立った道に進む** (`if / else if` の連鎖と同じ。[process-flow-runtime-conventions.md §11.5](process-flow-runtime-conventions.md) で確定)。「それ以外」は、どれにも当てはまらないとき。ガードの「それ以外」は、「次の工程へ進む」
- 「または」は、列に分ける (道 A の 1 / A の 2)。「かつ」の中の括弧は、分配して列にする (`A かつ (B または C)` → 2 列)。同じ条件とその反対 (`==` と `!=`) の行は 1 つにまとまる。ただし、厳密な比較 (`===`) と緩い比較 (`==`) は別の行 (null / undefined の扱いが違うため)。行の向き (「ある」か「ない」か) は、マスを触っても、反転して見えない。列が 16 を超える式・三項演算子は、表にしない
- **見落としの指摘** (表の下): 先に成り立つ道に隠れて選ばれない道 (⚠) / 同時に成り立つ場合がある道 (ⓘ。そのときは上の道が選ばれる。同じ項目が別々の値と等しい道は、重ならない) / 「それ以外」が無いときの、**どの道にも入らない組み合わせ** (⚠。例を最大 3 つ。条件 8 個まで。同じ項目が複数の値と同時に等しい、起こらない組み合わせは出さない) / 条件が空の道・条件が食い違う列 (⚠。同じ条件が成り立つとも成り立たないとも・別々の値と等しい・数の範囲が重ならない・「ない」と値の一致・「はい」と「いいえ」)。起こらない組み合わせは、抜けにも重なりにも出さない (同じ項目の `==` と数の範囲だけ。「金額 > 100」と「金額 > 500」の包含や、ほかの項目をまたぐ関係までは見ない)。「すべての組み合わせが入る」は、値が空・未設定のときを調べていない。表にできない道 (エラーを捕まえる道など) があると、抜けの調べは、表にできる道だけ (ⓘ)
- 直す (編集中): マスをクリックで ○ → × → － (「成り立たない」を作れない式の行は ○ ↔ －)。その道の条件の式を、列から**組み立て直す** (触らない道の式は、そのまま。直した道は「または」の列に展開した形になる)。「＋ 条件の行を足す」(条件の選び、または式)・行の「直す」(すべての道に反映。× の列は反対の条件になる)・行の × (外すと条件が空になる道や、「または」の 1 列が空になる道があるときは、消せない)・「＋または」(その道に列を足す)・「列を外す」(「または」の 1 列を外す)。**「または」の 1 列が、すべて「－」になるマス操作は断る** (式に書けず、捨てると道が黙って狭くなるため)。表にできない道 (エラーを捕まえる道・三項演算子など) は、行の置き換え・削除の対象にならないので、その旨を通知する。条件を足すとき、「～ がある (`!= null`)」は、その項目の中身を使う条件より前に入る (左から順に調べるため)・「＋ 道 (列) を足す」
- ひな型「条件の組み合わせで分ける (判定表)」: 条件が空の道 A・B と「それ以外」が入り、判定表が開く。表で ○ × を付けて決める
- 図の「判定表」(UI 改善提案 #149。`utils/decisionTable.ts`) は、枝の一覧と文字の比べだけ。ここの判定表は、条件を部品に分けて、組み合わせの抜け・隠れを調べる

## 確認済みの置き場所

設計の原本ではなく、確かめた人の手元の記録として、**ブラウザ (localStorage)** に持つ。キーは `harmony.processFlow.reviewed.<ワークスペースの ID>:<処理フローの ID>:<アクションの ID>`。設定の書き出しには含めない (別のブラウザでは意味がない)。書く直前に保存済みの内容から作り直すので、複数のタブで付けても、互いの分を失わない。値は、工程 ID → 工程の指紋 (入れ子の中は含めない、その工程そのものの内容)。画面を開いただけで、原本は書き換わらない。人ごとの記録なので、共有はしない。

## schema の追加 (処理フロー schema v3、実行には影響しない・任意)

設計者の承認 (2026-10-19、リリース前・抜本的な見直しも可) のもとで、表示のための任意項目を 3 つ足した。

| 場所 | 項目 | 内容 |
|---|---|---|
| 全工程 (`StepBaseProps`) | `heading` (1〜80 文字) | この工程から、新しい見出し (区切り) を始める。最上位の工程だけで意味を持つ |
| `outputBinding` | `label` (1〜40 文字) | 結果変数の呼び名 (「取引先」「受注合計」)。条件・変数の一覧で、名前の代わりに出す |
| 繰り返し (`loop`) | `collectionItemLabel` (1〜40 文字) | 繰り返しの 1 行の呼び名 (「明細の行」) |

`label` が無い変数は、名前 (`customer`) のまま出す。入力 (`@inputs.x`) は、アクションの入力の `label` を使う。AI が処理フローを作るときは、見出しと呼び名を付ける (`ai-skills/create-flow/SKILL.md`)。

## 限界 (いまの版)

- 直せるのは、説明・条件・実行条件・テーブル・操作・返す応答・結果の変数 (作り方を含む)・並び・見出し・道と枠・判定表・入力チェックのルール・SQL の文・承認者と期限・外部システムの呼び方。それ以外の細かい項目 (承認の種類・エスカレーション・リクエストの中身・認証・SQL の WHERE を部品で組む・テーブルの列の選びなど) は、行の「カードで開く」から
- 条件を選びで直せるのは、「式」の条件だけ。エラーを捕まえる道 (tryCatch)・更新 0 件・外部呼び出しの結果の条件は、閲覧と同じ言葉で出し、直すのは「カードで開く」から (直すと、エラーコードなどの中身が消えるため)
- 条件の選びは、もとの式の意味を変えない: 厳密な比較 (`===` `!==`) や `!= true` は、触らなければ、そのまま書き戻す。部品にできない式は、式のまま直す。実サンプルの全条件で、往復して変わらないことを試験している
- 条件の変数の候補は、検査 (identifierScope) と同じ取り決め: その工程の「前」にあって、同じ並びか外側の並びで作られるもの。分岐の道・繰り返しの中で作った変数は、そのあとの外側の工程から使える。まとまり (トランザクション) の中の変数は、外からは使えない (まとまりの「確定したあと」「取り消したあと」の中からは見える)。別の道 (兄弟の枠) の中の変数は使えない。入力は `@入力名` の短縮形でも、「作られていない」と言わない
- 結果の変数の名前を変えると、同じ名前を作るすべての工程と、使う式 (`@x` `@var.x` `@var.action|loop|…x` `@var.step|tx.<工程>.x`。メールアドレスの `@` と、`@conv.x` のような別の名前空間は除く) を直す。使えない名前: 処理の外の名前空間 (inputs・var・conv・env・secret・const・msg・global・session)・処理の外から来る値・ほかの変数
- 「見出し」は位置に付く。見出しのある工程を上へ動かすと、見出しは、動かした工程ではなく、その位置に残る
- 工程の入れ子のうち、外部呼び出しの結果の副作用 (`errorHandling.outcomes.*.sideEffects`) は、編集の操作は届くが、流れでは出さない (サンプルでは使われていない)
- 「移す」の行き先は、その枠の最後だけ (途中の位置は、ドラッグか、移したあとの ↑↓)
- 変数の「下ごしらえ」は、一部だけ: 条件の候補は、その位置より前で作られる変数に絞り、まだ作られていない変数を式に書くと知らせ、名前を変えると使う式も直す。繰り返しの中で足す変数の宣言 (代入方式・初期値) は、結果の変数の「作り方」でできる。検索 (SELECT) の結果が 1 件か一覧かは、SQL から推定して知らせる (下の「検索の結果は 1 件か一覧か」)
- 変数のプロパティ (`@customer.isActive` の `isActive`) の呼び名は、名前のまま (SQL の別名・テーブルの列の論理名との対応は、未対応)。`length` は「長さ(件数)」(型が分からないので、文字数とも件数とも言えない)
- 条件の言葉への直しは、「A が B と等しい / より大きい」「かつ / または」まで。判定表の「どの道にも入らない組み合わせ」の調べは、条件を独立した真偽として数える (「金額 > 100」と「金額 > 500」の包含関係までは見ない)。同じ項目が別々の値と等しい道の排他だけ、考えに入れる
- DB の WHERE の印は、最初の `WHERE` から取る (サブクエリの中の WHERE では、途中までになることがある。全文は「実装」で見える)
- 見出し (`heading`) は、最上位の工程でだけ意味を持つ (schema の説明だけで、検査はしていない)。AI への指示 (`create-flow`) では、8 工程以上のときに付けることを**勧める** (検査では強制しない)
- 条件の言葉の細部: `null == @x` (左が値) は「null が x と等しい」と出る。文字列の比較で、空白が少し広く出る
- 確認済みの記録は、消えた工程の古い分を掃除しない (ブラウザに残り続ける。「すべて外す」で消せる)
- 約 360 工程の大きな流れの速さ (2026-10-20 に実測): 実ブラウザ (Chromium・開発サーバ) で、流れを開く 0.9 秒・編集を始める 0.5 秒・1 回の操作の描き直し 0.5 秒・判定表を開く 0.1 秒、画面の固まり (long task) は最大 0.44 秒 (`e2e/perf-process-flow-story.spec.ts`。回帰には含めない)。jsdom の単体試験 (`story/ProcessFlowStory.perf.test.tsx`) でも、どれも 0.5 秒未満。約 1080 工程 (2026-10-24 に実測。`PERF_STORY_REPEAT=60`): 流れを開く 2.1 秒・編集を始める 1.5 秒・1 回の操作の描き直し 1.0 秒・判定表を開く 0.2 秒、画面の固まりは最大 1.3 秒。工程数にほぼ比例する。使える範囲だが、操作ごとに 1 秒ほど待つ。編集の操作ごとに行すべてを描き直す作りのため (速くするには、行ごとのメモ化と、操作が変えていない部分の参照を保つ作り直しが要る)。サンプルの処理は最大でも 1 アクション 26 工程なので、直していない。1000 工程を超えるときは、共通処理への切り出しを勧める
