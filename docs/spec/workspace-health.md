# ワークスペースの健全性

ファイルが壊れた・食い違った・途中で止まった、を見つけて直すための仕組み。**読むだけの検査**と、**利用者・AI が明示的に実行する保守**に分かれる (開いただけ・検査しただけでは、原本は書き換わらない)。

## 検査 (読むだけ。設計の「要確認」に出る)

`backend/src/workspaceHealth.ts` の `scanWorkspaceHealth`。データが変わらないあいだは結果を使い回す (`dataSignature`)。ダッシュボードの「設計の要確認」・設計書の「要確認事項」・`designer__check_design` に出る。

| 区分 | 内容 |
|---|---|
| error | **JSON として読めない**ファイル (誤りの場所を「n 行目 m 桁目付近」で示す)。このままでは一覧・検査・設計書に含まれない。直すか、保存前の版 ([file-backup.md](file-backup.md)) から戻す |
| warning | **大きすぎる**ファイル (20 MB 超。読み込みを避けるので、一覧・検査に含まれない) |
| warning | **ファイル名と中の id が違う** (一覧・参照がどちらかを見失う) |
| warning | 一覧 (`harmony.json`) にあるのに**ファイルが無い**項目 |
| info | 一覧に**載っていない**設計ファイル (読み出しでは一覧に足して扱っている) |
| info | **uuid がファイルに保存されていない**設計 (読み出しでは、種類 + id から決めた値で補っている。[workspace.md](workspace.md)) |

## 保守 (明示的な操作。既定は予行)

| 操作 | 画面 | AI (MCP) |
|---|---|---|
| 一覧とファイルの食い違いを直す (載っていないファイルを一覧に足す / ファイルが無い項目を外す / harmony.json の最上位にある旧形式の項目 `tables` `screens` `processFlows` `edges` `updatedAt` を取り除く。v3 のスキーマに無く、画面がワークスペースを開けなくなるため。#1568) | ダッシュボードの要確認パネル「一覧の食い違いを直す」(予行の件数を確認してから実行) | `designer__repair_registry` (`apply: true` で実行) |
| 未保存の uuid を、読み出しで補っている値で固定する (値は変わらない) | 同「uuid を固定する」 | `designer__persist_uuids` (`apply: true` で実行) |

ダッシュボードの要確認パネルには、種類 (画面・処理フロー・テーブル・業務フロー・帳票・その他) ごとの件数 (0 件もあわせて) が出る。

## 複数ファイルの操作の復旧 (操作ログ)

改名 (`designer__rename_entity`) は、参照元の更新・新しいファイルの作成・古いファイルの削除と、複数のファイルを書く。途中の失敗は操作の中で元に戻す (snapshot からの復元) が、**プロセスが強制終了した・電源が落ちたとき**は、その処理が動けず、一部だけ書き換わった状態が残る。

- 書き換える前に、元の内容を `<ワークスペース>/.harmony-journal/<時刻>-<id>.json` に書く (書き終えた記録だけが復旧の対象)
- 操作が終わったら (成功・失敗のどちらでも、元に戻し終えたら) 記録を消す
- 次に、そのワークスペースへの最初の要求 (画面の操作・AI の tool) のとき、残っている記録があれば、元の内容に戻し、新しく作ったファイルを消す (操作の前の状態に戻る)。戻したファイルは、同じパスが「消す」側に入っていても消さない。読めない・不正な記録は戻さずに残す (警告ログ)
- 記録には、書いたプロセスの**起動ごとの識別子** (instanceId)・pid・ホスト名を持たせる。**持ち主が生きている記録は、進行中の操作なので戻さない**: このプロセスの起動中の記録 (識別子が同じ) / 同じホストで、別の pid が生きている記録 / 別のホスト (別のコンテナが同じボリュームを使う) の 10 分以内の記録。再起動した自分 (pid が同じ。配布の Docker は毎回 pid 1) や、死んだ pid の記録は、残骸として戻す。飛ばしたときは警告ログに出す
- 成功した改名で、記録の削除に失敗しても、改名は巻き戻さない (記録は、持ち主のプロセスが終われば、次の復旧で扱う)
- 対象は改名の主な書き込みまで。**改名の取り消し (`designer__undo_rename`)・改名後に続く業務フロー・帳票の参照更新・編集セッションの対象 id の移行・`designer__apply_rename_mapping` は、記録の対象外** (取り消しは、元の内容を持つ操作の記録 (undo) から戻す。参照更新の失敗は警告として返し、改名全体は失敗にしない)

実装: `backend/src/operationJournal.ts`

## 旧形式 (GrapesJS) の画面

旧形式の画面、または旧デザイン (`.design.json`)・旧画面項目 (`screen-items`) だけが残っていて実体が無い画面は、**読み出しではメモリ上で変換するだけ**で、ファイルを書き換えない (uuid も、種類 + id から決めた値)。設計書・検査・一覧の読み出し (`readEntityReadOnly` / `listEntitiesReadOnly`) も、旧形式は変換して返す。健全性の検査・一覧の修復・uuid の固定は、旧形式・旧配置の画面を「ある画面」として扱う (一覧から外さない・uuid を書かない)。保存・削除など、これから書き込む操作のときに初めて、旧形式を `<id>.design.json` へ退避して実体を書く。これで「読んだだけで原本が変わる」例外は無くなった。
