# 状態遷移・初期データ・非機能要件・ジョブ

業務の「状態の移り変わり」「最初から入れておくデータ」「性能などの目標」「定期的に動く処理」を、設計として残す使い方です。メニューの「汎用定義」から、種類を選んで開きます。

| 種類 | 何を書くか | 例 |
|---|---|---|
| 状態遷移 | 状態の一覧と、どの契機でどの状態へ移るか。移す処理フローを結びつける | 注文: 注文済み → 確認済み → 出荷済み → 配達済み |
| 初期データ | テーブルに最初から入れておく行 | 店舗マスタの 3 店舗 |
| 非機能要件 | 測るもの・目標値・対象の処理フロー | 注文確定の応答時間 p95 ≦ 2000 ms |
| ジョブ | 実行の時刻・再実行の方針・実行する処理フロー | 毎朝 6 時に KPI を集計 (失敗したら最大 3 回) |

## 状態遷移

1. 「+ 状態を足す」で状態を入れる。名前はコードの値 (`pending` など)、呼び名は画面での言い方。**最初の状態は 1 つ**、これ以上動かない状態は「終わり」にチェック
2. 「+ 遷移を足す」で、元の状態・先の状態・契機 (例: 出荷を確定する)・条件を入れる。遷移を起こす処理フローを選ぶ
3. 状態を入れるテーブルのカラムは、設計書や AI への手がかりになる (任意)

点検 (「分析」の要確認) が、最初の状態がない・たどり着けない状態・行き止まり・存在しない状態への遷移を知らせます。設計書には、表と状態遷移図 (Mermaid) が載ります。

## 初期データ

対象のテーブルを選び、行を JSON の配列で書きます (キーはカラムの物理名)。必須のカラム (`*`) を欠かさず、主キーが重ならないようにします。点検が、カラムの違い・必須の欠け・数でない値・長さの超過・主キーの重複を知らせます。

INSERT 文にするには: `npm run export:seed -- <ワークスペース>` (`--format json` で JSON)。

## 非機能要件・ジョブ

- 非機能要件: 対象の処理フローに「SLA」の宣言がないと、知らせが出ます。要件の数値を、処理フローの SLA にも写してください
- ジョブ: cron は 5 つの欄 (分 時 日 月 曜日)。`0 6 * * *` は毎朝 6 時。間隔は `PT15M` (15 分) の形

AI に頼むときは、[AI のレシピ](../spec/ai-recipes.md) の「状態遷移・初期データ・要件・ジョブを設計する」を渡すと、同じ手順で作ります。
