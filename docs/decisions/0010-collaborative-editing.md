# 0010 共同編集はいまは入れない

**状況**: ISSUE #855 は、Dify v1.14 の CRDT 方式 (loro-crdt) によるリアルタイム同時編集を調べ、Harmony で採用するかを問うた。Harmony の編集は、サーバ側の下書き + ロックの悲観的な排他で、明示保存モデル (開いただけで原本を書き換えない)。

**決めたこと**: CRDT による同時編集は**入れない**。複数人・AI が同じ設計に触れる場面は、次の既存の仕組みで足りるものとして扱い、足りない点が実際に出たら、別の判断として起こす。

- 同じ設計の同時編集: 編集のロック ([edit-session-draft.md](../spec/edit-session-draft.md))。ほかの人が編集中なら、読むだけで開き、「前回の編集の続き」で引き継げる
- 別の経路 (AI・ファイル・git) での更新: 外部更新の検知 ([external-change-detection.md](../spec/external-change-detection.md)) と、保存前の版 ([file-backup.md](../spec/file-backup.md))
- 衝突: 保存時の版の確認と、衝突の判定 ([ui-first-run-ux.md](../spec/ui-first-run-ux.md))
- AI との分担: AI は下書きのセッションを借りて直し、人は保存で確定する (`onBehalfOfSession`)

**理由**:
- 最適化の軸が逆: Dify は人間の同時編集が主、Harmony は「AI が読む・直す」「スキーマの整合」が主。CRDT の自動マージ (LWW) は、必須項目が空になる・参照が切れるといったスキーマ違反を、黙って作りうる。Harmony は違反を `check_design` で人が確かめる前提
- 一次成果物は JSON ファイル。CRDT の文書 (Loro) を真実点にすると、ファイル ⇄ 文書の二重管理になり、git・AI (MCP) の直接の読み書きと衝突する
- 規模: 同じ設計を同時に直す場面は、設計書の単位では少ない (画面・処理フロー・テーブルが別ファイル)。ロックの粒度は、ファイル単位
- 費用: 通信 (relay)・状態の同期・取り消し・権限・テストの全層に及ぶ。MCP は要求ごとに作り直す設計 ([0007](0007-mcp-stateless.md)) で、押し出しの通知も持たない

**選ばなかった案**: loro-crdt の採用 (上の理由) / 工程単位のロック (取り消しと保存の単位が合わない。必要になれば、ロックの粒度の細分化から) / 閲覧だけの同時表示 (presence: 編集中の人の表示)。presence は、費用が小さく価値がありうるので、実際に「誰かが編集中で開けない」不満が出たときの最初の候補にする。

**結果**: #855 は、この記録を残して閉じる。再検討の条件: (1) 同じファイルで編集が衝突した報告が繰り返し出る、(2) 設計を細かい単位 (工程) に分けて保存する方針に変わる、のどちらか。
